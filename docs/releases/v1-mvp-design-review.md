## (1) Interfaces / data shapes a parallel worker will code against inconsistently

**BLOCKER — `Cluster.best_move` has no source in `aggregate`'s frozen inputs.** `aggregate(scored_moves, deviations)` receives `(PlyRecord, Severity)` and `DeviationFlag`. `PlyRecord` = (game_id, ply_index, fen_before, move_uci, move_san, is_my_move, eco); `Severity` = (cp_loss, winprob_drop, klass). None carries an engine best move, yet `Cluster.best_move` is required by O2 and by `report.py`. U6 must either re-analyse (an engine dependency absent from its contract) or drop a field the report is specified to print. Fix: freeze `aggregate(scored_moves: Sequence[tuple[PlyRecord, Severity]], deviations: Sequence[DeviationFlag], best_moves: Mapping[tuple[str, int], str]) -> list[Cluster]`, key `best_moves` by `(game_id, ply_index)`, and pin the form as SAN (same space as `my_moves`).

**BLOCKER — clustering keyed by `(eco, fen_before)` splits recurring positions, which is the product's whole premise.** The only ECO available is *game-level* (chess.com `[ECO]` PGN tag / archive `eco` URL), not per-ply, so two games reaching the same board by transposition carry different codes. Measured on one real month archive (548 games, plies 1–14): **321 of the 811 recurring positions (40%) carry more than one ECO tag**. A position played 3 times, once under each of 3 tags, becomes three clusters with `occurrences=1` and vanishes from a frequency×severity ranking. This also violates PRD decision 1 ("identical-FEN aggregation works here"). Fix: key clusters on `fen_before` only; carry `eco` as a display label (most frequent among contributing games); state explicitly in the record that FEN is the discriminator and ECO is a label.

**MAJOR — `eco` is optional in the real data but typed `str`.** In the same archive, 65/548 games have no archive `eco` field and 11/548 have no `[ECO]` PGN tag (~12%). `GameRecord.eco:str` / `PlyRecord.eco:str` / `Cluster.eco` are frozen as non-optional, and no precedence is pinned when JSON and PGN disagree. Fix: declare `eco: str | None` on `GameRecord`/`PlyRecord`/`Cluster`, pin precedence (PGN `[ECO]` tag over archive `eco` URL), and pin the report's rendering for `None`.

**MAJOR — `fen_before` as an identity key carries the halfmove clock and fullmove number.** `board.fen()` (python-chess default, verified) emits all six fields, so the same board reached by transposition at a different move number is a different string → separate clusters and a separate cache entry. Measured on the real archive: 4,738 distinct full-FEN keys vs 4,634 for the first four fields (104 duplicated engine analyses; 2,898 vs 3,002 recurrences collapsed). The eval cache — described in bead `chess-4uy` as "the main speedup" — silently loses those hits. Fix: freeze `position_key(fen) = " ".join(fen.split()[:4])` and require both the cluster key and the eval-cache key `(position_key(fen), depth)` to use it; keep the full FEN for display only. Also pin the en-passant flavour (`board.fen()` uses `en_passant="legal"` and normalises an impossible ep square to `-`, verified; `en_passant="fen"` and `shredder_fen` produce different strings, so a hand-written fixture key will never match).

**MAJOR — `cache_hit_rate` is required in `summary` but no frozen interface exposes it.** The record says "`cache_hit_rate` is a `cli.py` concern, not `engine.py`'s", yet `analyse(fen) -> EvalResult` returns no hit/miss signal and only `engine.py` can know. O1/O5 also require it visible while running. Fix: freeze `EngineService.hits: int` / `.misses: int` counters in the contract table and define the denominator (`hits / (hits + misses)`).

**MAJOR — the frozen table omits the constructors and the two cross-unit functions U8/U6 call.** `extract_opening_plies` and `download_all` are not in the record's frozen contracts; `EngineService`'s constructor is not either (bead `chess-4uy` says `EngineService(stockfish_path, depth, cache_path)`; U8 will as likely write `EngineService(Config)`). `Threads=2`/`Hash=128` appear under *Host limits* but no interface can carry them (no options parameter). Fix: add `extract_opening_plies(game_record: GameRecord, max_plies: int) -> list[PlyRecord]`, `download_all(username: str, cache_dir: str) -> list[GameRecord]`, and `EngineService(stockfish_path: str, depth: int, cache_path: str, *, options: dict[str, str] | None = None)` with `{"Threads": "2", "Hash": "128"}` defaults, plus "U8 opens exactly one `EngineService` for the whole run".

**MAJOR — U8 must build `fen_after` itself, which the record forbids.** "Nothing else should re-implement PGN walking, FEN construction…" yet `move_severity(eval_best, eval_after, my_color)` needs the post-move position and `PlyRecord` has only `fen_before`. Fix: add `fen_after: str` to `PlyRecord` (U3); this also makes `positions_evaluated` computable and removes a terminal-position recomputation in U8.

**MAJOR — sort ownership is double-specified.** `cluster.py` owns `rank_clusters(clusters)` and `report.py` is specified as "for each of the top_n clusters by composite_score". If U8 passes unsorted clusters the markdown ranks are silently wrong. `top_n` also exists both as `Config.top_n` and as a `render_report` parameter. Fix: state `aggregate` returns unsorted, `rank_clusters` sorts, `render_report` re-sorts defensively, and `Config.top_n` is the value passed (drop the parameter or name which wins).

**MAJOR — env-var names unpinned and contradicted by a bead's named test.** `chess-bb8` names `test_config_env_override (CHESSLEAK_DEPTH=22 -> analysis_depth==22)`; the record only says "`CHESSLEAK_*`", which reads as `CHESSLEAK_ANALYSIS_DEPTH`. Fix: publish the full table (`CHESSLEAK_USERNAME`, `_STOCKFISH_PATH`, `_ANALYSIS_DEPTH`, `_OPENING_PLIES`, `_CACHE_DIR`, `_WIN_PROB_K`, `_BOOK_BAND_CP`, `_TOP_N`) and reconcile the `CHESSLEAK_DEPTH` test.

**MAJOR — `Config()` cannot satisfy `chess-bb8`'s `test_config_defaults`.** The bead declares `username:str, stockfish_path:str` with no defaults while requiring `Config()` to yield documented defaults, and the record's table silently dropped the bead's documented `cache_dir="~/.cache/chessleak"`. Fix: give `username: str = ""` and `stockfish_path: str = ""` (or a `default_factory` resolver), restore the `cache_dir` default, and paste the exact expected default block into the record.

**MAJOR — `GameRecord` has no `rules`/`initial_setup`, and non-standard-start games are ~12% of a real archive.** Measured in one real month: 483 `chess`, 33 `chess960`, 32 `oddschess`, with non-standard `initial_setup` FENs. Their opening positions can never recur, so each injects a one-off `occurrences=1` cluster that still competes in the ranking. Fix: add `rules: str` and `initial_setup: str` to `GameRecord`, pin "skip non-`chess` rules and non-standard `initial_setup`", and surface the skipped count in `summary`.

**MINOR — `GameRecord.result` mapping unpinned; the real values are verbs.** Per-colour `result` counts from that archive: win 271, resigned 184, timeout 32, repetition 24, checkmated 19, agreed 7, insufficient 5, timevsinsufficient 3, stalemate 2, abandoned 1 — not `1-0/0-1/½-½`. Fix: pin `result` to the PGN-style string via a stated table, or keep `white_result`/`black_result` verbatim.

**MINOR — `my_moves: Counter` key type unpinned, and SAN/UCI forms are mixed across contracts.** `EvalResult.best_move` is UCI, `DeviationFlag.best_move` is SAN, `Cluster.my_moves` is unspecified. Fix: pin `my_moves: collections.Counter[str]` keyed by SAN and `Cluster.best_move: str` in SAN; keep UCI in a separate field if the report needs it.

**MINOR — `first_deviation(ply_records, engine, band_cp)` has no game parameter.** `DeviationFlag.game_id` can only come from `ply_records[0].game_id`, so passing all games' plies in one call collapses the run to one flag. Fix: state it is called once per game with that game's window.

**MINOR — `EvalResult` cannot represent a terminal/rootless position.** Fast mates inside a 15-ply window are common (19 checkmates in one real month). On a mate/stalemate board Stockfish returns no pv and `bestmove 0000`, so `best_move: str (UCI)` has no value and `pv[0]` raises `IndexError`. Fix: `best_move: str | None` and pin that U5 short-circuits a terminal `eval_after` (drop = 1.0, `blunder`) without needing a best move.

**MINOR — summary field definitions unpinned** (`positions_evaluated`, `flagged_mistakes`, `games_analyzed` are computed in one unit and rendered in another). `flagged_mistakes` in particular could mean `klass != ok`, `klass in {mistake, blunder}`, or either-or-deviations. Fix: define each in the record.

**MINOR — positional vs flag username.** PRD acceptance and `chess-uow` say `chessleak analyze <username>`; brief O1 says `analyze --username <account>`; the record doesn't resolve it. Fix: PRD is authority — positional canonical, `--username` as alias, and pin exit codes (including for zero games / zero clusters).

**MINOR — `cp_to_winprob(cp, k)` signature admits no mate** while the record attaches "mates map to ±1.0" to that function. Fix: state the mate mapping lives in `move_severity` and `cp_to_winprob` is cp-only.

## (2) Sign / unit-conversion errors the pinned conventions do not prevent

**BLOCKER — the white-POV rule has no pinned mechanism, and python-chess's default is side-to-move POV.** Verified in python-chess 1.11.2: `UciProtocol._parse_uci_info` sets `info["score"] = PovScore(Cp(...), root_board.turn)`; conversion is the explicit `PovScore.white()`. A worker reading `info["score"].relative` on a black-to-move FEN silently sign-flips every score — the exact failure the PRD names ("reporting win-probability numbers that flip sign depending on the player's color") and the record's own *Product fit* failure list. Fix: pin the line in `engine.py` (`score = info["score"].white()`, one line, commented) and add a real-engine integration test asserting a **black-to-move** mate-in-1 returns `mate == -1` and a black-to-move lost position returns negative cp. Note Risk 4 claims "the integration tests for black-side play are the guard", but no such test exists: `chess-4uy`'s `assert mate==1` passes under either convention if the fixture is white-to-move, and *rewards* the bug if the fixture is black-to-move.

**BLOCKER — the "conversion happens in `severity.py` and nowhere else" rule forbids the conversion `book.py` needs.** `cp_gap` is the difference between the engine eval before and after the player's move. Under white-POV-only numbers, a black player's *improving* move reads as a drop, so deviations for black invert and `book_band_cp=30` flags exactly the in-book moves. Fix: state that POV conversion is a shared helper — e.g. `severity.to_my_pov(eval: EvalResult, my_color: str) -> EvalResult`, or an `EvalResult.white_pov_to(color)` method on the frozen dataclass — that `book.py` may import, and pin `cp_gap >= 0` means "worse for the player".

**BLOCKER — `win_prob_k=0.004` with thresholds 0.30/0.15/0.07 makes a "blunder" require a ~3.5-pawn loss.** From the record's own formula `1/(1+exp(-k·cp))`: drop ≥ 0.30 ⇒ cp_loss ≈ 347; ≥ 0.15 ⇒ ≈ 159; ≥ 0.07 ⇒ ≈ 72. So a 100 cp blunder classifies `inaccuracy`, a 50 cp error classifies `ok`, and nothing short of a ~3.5-pawn swing is ever a `blunder` — against the conventional 50/100/200 cp bands (lichess: k=0.00368 with 0.05/0.10/0.20). On real opening data `flagged_mistakes` will be near zero and O3's labels will not match any chess product the operator knows. Fix: pin the classification in cp (`ok <50, inaccuracy 50–100, mistake 100–200, blunder ≥200`) and derive win-probability for display only, or adopt the lichess pair (k≈0.00368, 0.05/0.10/0.20); add a U5 integration assertion that a 100 cp loss is `blunder` and a 30 cp loss is `ok`.

**MAJOR — `composite_score = occurrences * avg_winprob_drop + 0.05 * deviation_count` mixes a frequency-scaled term with an absolute one.** The bonus's effective weight swings ~20× with cluster size: at `occurrences=1` an all-`ok` cluster with one deviation scores 0.05 and beats a real single 100 cp blunder cluster (0.0996 only narrowly; a 50 cp error scores 0.0498 and loses to it), while at `occurrences=20` the same bonus contributes 0.05 against a ~1.0 score and is noise. The constant0.05 is silently tuned to the win-probability scale, which the previous finding shows is itself wrong. Fix: pin `composite_score = occurrences * (avg_winprob_drop + 0.05 * deviation_rate)` with `deviation_rate = deviation_count / occurrences`, and re-derive 0.05 from the k you actually choose.

**MINOR — mate → ±1.0 ignores distance** (explicitly allowed by the record), making mate-in-1 and mate-in-12 identical and a forced-but-unfound mate score 0.0. Acceptable for v1, but say so in the record rather than leaving it implicit.
